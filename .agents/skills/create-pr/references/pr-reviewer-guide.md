# PR 본문: 리뷰어 중심 작성 규칙

PR 본문은 리뷰어가 변경의 의도, 구현 구조, 주요 계약과 위험을 판단하기 위한 문서입니다.
작업자가 수행한 절차와 자동화 도구가 이미 확인하는 일반적인 완료 조건은 본문에 기록하지 않습니다.
PR의 제목, 브랜치, 푸터, 권한 및 게시 절차에는 저장소의 `AGENTS.md`를 우선 적용합니다.

## Must

- **변경 목적과 효과를 설명해야 합니다.** 무엇을 왜 변경했으며, 외부에 관찰되는 동작·계약·호환성이 어떻게 달라지는지 명시합니다.
- **중요한 구현 방식을 설명해야 합니다.** 주요 객체·계층의 책임과 협력, 처리 흐름, 상태 및 트랜잭션 경계 중 변경 이해에 필요한 정보를 제공합니다. 단순 클래스 목록 대신 실제 동작을 설명합니다.
- **핵심 설계 결정의 근거를 제시해야 합니다.** 선택한 방식의 이유와 의미 있는 트레이드오프를 설명하며, 코드만 읽어서는 파악하기 어려운 맥락을 우선합니다.
- **구체적인 검토 대상을 제시해야 합니다.** 리뷰어가 확인해야 할 동작 계약, 경계 조건, 예외 처리, 기술적 위험 또는 설계 선택을 특정합니다. 해당 계약·코드·문서로 직접 연결합니다.
- **의미 있는 제약과 미검증 범위를 밝혀야 합니다.** 의도적으로 제외한 기능, 알려진 한계, 마이그레이션·배포·롤백 조건을 검토 판단에 영향을 주는 경우 명시합니다.
- **설명에 근거를 제공해야 합니다.** 관련 설계 문서, 요구사항, 공식 자료를 설명 위치에 연결합니다. 링크만 제공하지 않고 해당 자료가 어떤 판단에 필요한지 서술합니다.
- **복잡한 협력이나 순서는 시각화를 우선 검토해야 합니다.** Mermaid 다이어그램, 표, 스크린샷이 글보다 구조를 정확하게 전달할 때 활용하고 실제 구현과 일치하는지 확인합니다.
- **최종 변경과 일치해야 합니다.** PR 본문을 최종 Diff와 대조하고 리뷰 반영으로 계약이 바뀌면 본문을 갱신합니다.

## Must Not

- **정상적인 개발 완료 조건을 기록하지 않아야 합니다.** 전체 테스트 성공, 빌드·린트·포맷팅 완료, 일반적인 Git 충돌 해결, 브랜치 동기화, `AGENTS.md` 준수 사실을 나열하지 않습니다.
- **구현 과정의 일지를 작성하지 않아야 합니다.** 테스트 개수, TDD의 RED·GREEN 순서, 테스트 작성 순서, 구현 단계와 커밋별 수행 이력을 본문의 성과로 표현하지 않습니다.
- **Diff를 반복해서는 안 됩니다.** 변경 파일의 단순 나열, 코드 한 줄씩의 설명, 커밋 로그 복제를 피하고 설계·동작에 관한 정보를 남깁니다.
- **모호한 검토 지시를 작성하지 않아야 합니다.** `테스트 확인`, `예외 처리 검토`, `코드 품질 검토`처럼 구체적인 계약과 판단 기준이 없는 문구를 사용하지 않습니다.
- **의미 없는 섹션을 채우지 않아야 합니다.** `검증`, `테스트`, `배포` 등의 고정 섹션을 만들거나 일반적인 성공 결과로 채우지 않습니다.
- **검증하지 않은 사실을 단정하지 않아야 합니다.** AI 생성 요약·다이어그램, 성능 향상, 안정성 보장, 미구현 동작을 검증 없이 주장하지 않습니다.
- **이미 제공한 자료를 중복하지 않아야 합니다.** 장문의 로그, 전체 테스트 목록, 임시 로컬 파일 경로, 설명 없는 링크 나열을 제외합니다.

## 예외적인 검증과 실패

검증 자체는 프로젝트의 개발 절차에서 수행합니다. 검증의 존재를 PR 본문으로 증명하지 않습니다.
다음 내용은 리뷰·병합·배포 판단에 영향을 주는 경우에 한해 기록합니다.

- 검증 실패, 실행하지 못한 필수 검증, CI 부재 등으로 확신할 수 없는 범위
- 외부 시스템이나 실제 런타임과의 중요한 통합 동작을 확인한 근거
- 데이터 정합성, 장애 복구, 보안, 호환성에 직접 영향을 주는 중요한 관찰 결과
- 성공과 실패의 조건이 기존 계약과 달라지는 특수한 검증 결과

기록할 때는 **확인한 동작 또는 미확인 범위 → 판단 근거 → 영향** 순서로 설명합니다.
실행 명령이나 테스트 개수는 그 자체가 리뷰에 필수적인 경우에만 제시합니다.

## 다이어그램과 링크

- 책임과 의존 관계에는 구성 요소 다이어그램, 이벤트 순서에는 시퀀스 다이어그램, 상태 변경에는 상태 전이도를 고려합니다.
- 정보가 단순한 변경에는 다이어그램을 추가하지 않습니다. 다이어그램 자체가 중복 설명이 되지 않도록 합니다.
- 계약·설계 링크는 해당 문단 또는 검토 사항에 인접하게 배치하고, 가능하면 안정적인 버전·커밋의 문서를 사용합니다.
- 외부 링크를 읽을 수 없어도 중요한 결정과 영향은 본문에서 이해할 수 있어야 합니다.

## 기본 구성

```markdown
## 변경 내용

<변경 목적과 결과, 주요 구현 책임 및 협력, 중요한 설계 결정과 근거>

## 검토할 사항

- <구체적으로 검토할 동작·계약과 판단 기준, 관련 링크>

## 남은 범위와 제약

- <실제로 존재하고 리뷰 판단에 영향을 주는 제약과 미검증 범위>
```

마지막 섹션은 해당 사항이 없다면 생략합니다. 작은 변경에는 본문과 섹션 수를 줄입니다.
검토할 사항 역시 일반적인 품질 체크리스트로 채우지 않고, 실제 변경에서 판단해야 하는 부분만 작성합니다.
