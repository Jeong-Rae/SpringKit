# PR 작성과 점검을 위한 가상 사례

이 문서의 모든 사례는 **규칙의 적용 범위와 예외를 설명하기 위해 만든 가상의 상황**입니다. 실제 저장소, 특정 PR, 실제 수행한 테스트의 기록이 아닙니다. 숫자, 식별자와 설계 결정은 해당 사례의 가정일 뿐이며 다른 PR에 복사해 사용하지 않습니다.

사례를 정답 문장이나 PR 템플릿으로 취급하지 않습니다. 반드시 현재 PR의 Diff, 요구사항, 계약, 실행 근거를 확인한 다음 **비슷한 판단 문제와 비슷하지 않은 조건을 함께 비교**합니다. 사례가 실제 증거보다 우선하지 않습니다.

## 작은 오탈자 수정

**상황과 증거:** 사용법 문서에서 잘못 표기된 명령 옵션 한 글자를 정정했습니다. 명령 동작, 예제, 정책은 바뀌지 않았습니다.

- 부적절한 설명: `아키텍처 개선 및 검증 체계를 재정립했습니다. 설계 선택을 검토해 주세요.`
- 적절한 설명: `설치 안내의 명령 옵션 오탈자를 실제 옵션 이름으로 바로잡았습니다. 실행 동작은 변경하지 않았습니다.`
- **판단/반례:** 중요한 설계 선택이 없으므로 대안 비교, 다이어그램, 검토 요청을 만들 이유가 없습니다. 반대로 오탈자처럼 보이는 수정이 실제 명령 의미를 바꾸면 그 효과와 위험을 설명해야 합니다.

## 응답 계약 변경

**상황과 증거:** 요청의 필수 항목이 빠진 경우 서버가 기존 성공 응답 대신 유효성 오류를 반환하도록 변경했습니다. API 동작이 외부 호출자에게 보입니다.

- 부적절한 설명: `검증 로직을 정리하고 컨트롤러 3개를 수정했습니다.`
- 적절한 설명: `필수 항목이 없는 요청은 이제 성공 응답 대신 유효성 오류를 반환합니다. 기존 응답을 성공으로 처리하던 호출자는 오류 처리를 추가해야 합니다. 이 변경은 응답 계약 테스트에서 해당 입력에 대해 확인했습니다.`
- **판단/반례:** 호환성 변화가 핵심이라면 제목 또는 서두에 명시하고, 필요한 경우 입력별 이전/이후 결과를 비교합니다. 내부 구현만 바뀌고 외부 계약이 동일하다면 비호환성을 임의로 주장하지 않습니다.

## 저장 데이터 전환

**상황과 증거:** 새 버전부터 기록 형식을 바꾸어 기존 저장 데이터를 읽는 방식이 달라집니다. 이전 데이터에 대한 전환 도구는 아직 구현되지 않았습니다.

- 부적절한 설명: `저장소 계층을 정리하고 새 테이블을 추가했습니다.`
- 적절한 설명: `새 기록 형식을 도입하면서 이전 데이터는 새 조회 경로에서 표시되지 않습니다. 이번 변경에는 데이터 전환 도구가 포함되지 않았습니다. 기존 기록을 보존하고 조회할 수 있어야 하는지 검토해야 합니다.`
- **판단/반례:** 데이터 보존이 승인 판단에 중요한 경우 위험을 먼저 알립니다. 실제 데이터 이행을 완료하고 검증했다면 그 결과를 제시합니다. 단순한 저장 필드명 변경이라도 실제 호환성은 확인해야 합니다.

## 키보드 접근성 개선

**상황과 증거:** 메뉴를 열었을 때 키보드 초점이 메뉴 밖에 남는 문제를 수정했습니다. 작성자는 키보드 조작을 직접 시험했지만 보조기기 검증은 하지 않았습니다.

- 부적절한 설명: `접근성 테스트 완료. UI를 개선했습니다.`
- 적절한 설명: `메뉴를 열면 첫 번째 선택 항목으로 키보드 초점을 이동합니다. 키보드로 메뉴를 열고 이동하고 닫는 동작을 확인했으며, 화면 읽기 도구와의 동작은 확인하지 못했습니다.`
- **판단/반례:** 사용자에게 보이는 상호작용이 핵심이므로 시나리오와 범위를 설명합니다. 화면 전후를 비교해야 이해되는 경우에만 스크린샷을 추가합니다. 스크린샷을 사용하지 않았다는 이유로 결함 판정을 내리지 않습니다.

## 설정 우선순위 조정

**상황과 증거:** 서비스 시작 시 환경 변수에 설정값이 없으면 설정 파일 값을 사용하도록 순서를 변경했습니다. 운영 환경별 설정 자료가 서로 다릅니다.

- 부적절한 설명: `설정 파일과 초기화 코드를 수정했습니다.`
- 적절한 설명: `환경 변수가 지정된 경우 그 값을 사용하고, 없으면 설정 파일 값으로 대체하도록 우선순위를 변경했습니다. 운영 환경에서는 설정 파일의 기본값이 적용될 수 있으므로 현재 배포값과의 차이를 확인해야 합니다.`
- **판단/반례:** 기술적 설정 수단보다 **조건/기본값/영향 범위**를 중심으로 설명합니다. 모든 환경에서 설정이 동일하다면 존재하지 않는 위험을 강조하지 않습니다.

## 비동기 재시도 동작 변경

**상황과 증거:** 외부 요청 실패 시 두 작업이 같은 작업을 동시에 재시도해 중복 처리하는 문제가 있었습니다. 변경 후에는 같은 요청 식별자의 작업을 하나만 재시도합니다.

- 부적절한 설명: `워커, 큐, 락, 재시도기, 저장소를 전반적으로 개선했습니다.`
- 적절한 설명: `동일한 요청이 동시에 실패해도 재시도를 하나의 작업으로 제한합니다. 중복 재시도의 원인이 된 요청 식별자 공유 범위와 실패 후 해제 조건이 핵심 검토 대상입니다.`
- **판단/반례:** 실제 순서나 분기 조건이 승인에 중요하고 산문만으로 추론하기 어렵다면 흐름도를 고려합니다. 작업 순서가 단순하면 두 문장만으로도 충분합니다. 다이어그램을 만들었다는 이유로 동시성 안전성을 입증했다고 판단하지 않습니다.

## 작성 규칙 추가

**상황과 증거:** 기존 문서의 어휘를 통일하면서 별도의 새로운 `Should` 권고도 추가했습니다.

- 부적절한 설명: `문서를 읽기 쉽게 윤문했습니다.`
- 적절한 설명: `기존 설명문의 표현을 통일했습니다. 추가로 작성자가 검토 요청의 적용 조건을 구체적으로 적도록 권고하는 Should 규칙을 도입했습니다. 이 권고의 적용 범위와 기존 필수 규칙의 관계에 대한 검토를 요청합니다.`
- **판단/반례:** 표현 수정과 규범적 변경을 별도 의미 단위로 다룹니다. 실제로 규범 강도/적용 조건이 바뀌지 않은 문장 수정이라면 정책 변경이라고 과장하지 않습니다.

## 에이전트 수행 일지 혼입

**상황과 증거:** PR 본문에 Agent가 실행한 도구, 커밋 순서, 테스트 개수가 자세히 나열되어 있으나 실제 계약 변화는 한 문장뿐입니다.

- 부적절한 설명: `도구를 5개 적용했고 커밋을 4회 작성한 다음 테스트 120개를 통과했습니다.`
- 적절한 설명: `파일을 다시 처리할 때 기존 요청 식별자를 유지하도록 수정했습니다. 같은 식별자로 재처리하는 회귀 테스트에서 중복 기록이 발생하지 않음을 확인했습니다.`
- **판단/반례:** 운용 로그는 별도 보고로 분리하고 변경 동작과 직접 연결된 검증만 본문에 남깁니다. 특정 도구 버전이나 실행 명령이 재현에 꼭 필요한 경우에는 이를 제거하지 않습니다. `Agent`나 숫자가 등장했다는 이유만으로 위반을 확정하지 않습니다.

## 일부 검증 실패

**상황과 증거:** 핵심 조건의 단위 테스트는 성공했지만 운영 환경에 의존하는 연동 검사는 인증 설정이 없어 실행하지 못했습니다.

- 부적절한 설명: `모든 테스트가 통과했고 동작을 검증했습니다.`
- 적절한 설명: `단위 테스트에서 유효하지 않은 입력의 오류 반환을 확인했습니다. 외부 연동 검사는 인증 설정이 없어 실행하지 못했으며, 운영 환경과의 동작 일치는 확인되지 않았습니다.`
- **판단/반례:** 사실과 미확인을 분리합니다. 중요하지 않은 CI 성공 로그를 장황하게 나열할 필요는 없습니다. 반대로 중요한 검사 실패나 미실시 사실은 글을 줄이기 위해 삭제하지 않습니다.

## 구성 요소 책임 재분배

**상황과 증거:** 여러 구성 요소에 흩어진 입력 검증 책임을 한 경계에서 처리하도록 정리했습니다. 외부 입력과 출력 계약은 유지합니다.

- 부적절한 설명: `패키지 세 개를 옮기고 다섯 개 클래스를 새로 만들었습니다.`
- 적절한 설명: `입력 검증을 요청이 시스템에 들어오는 경계로 모아 하위 처리 흐름에서 동일한 조건을 반복하지 않도록 했습니다. 외부 요청과 응답 계약은 유지하도록 설계했으며, 기존 오류 조건은 계약 테스트로 확인했습니다.`
- **판단/반례:** 이전/이후 책임 소유자가 둘 이상이면 간단한 책임 비교표를 고려합니다. 계약이 달라지지 않았다는 주장은 수행한 확인 범위에서만 합니다. 클래스가 여럿 존재해도 책임 변화가 자명하면 구조도를 강제하지 않습니다.

## 성능 변경 주장

**상황과 증거:** 개발용 데이터 500건을 반복 조회한 측정에서 지연 시간이 줄었으나 운영 환경에서는 측정하지 않았습니다.

- 부적절한 설명: `조회 속도를 모든 환경에서 절반으로 개선했습니다.`
- 적절한 설명: `개발용 데이터 500건을 사용하는 반복 조회에서 지연 시간이 감소했습니다. 측정 환경 밖의 부하와 운영 데이터에 대한 성능 영향은 확인하지 않았습니다.`
- **판단/반례:** 측정 조건과 수치를 제시할 때 근거 자료가 실제로 존재해야 합니다. 표본이 없거나 환경을 모른다면 개선을 정량적으로 단정하지 않습니다. 결과가 없는 경우 성능 향상 자체를 주장하지 않습니다.

## 본문 수정 중 중요 정보 누락

**상황과 증거:** 초안에는 운영 환경에서 롤백이 어려운 변경이라고 적혀 있었지만, 문장을 줄이는 과정에서 해당 정보가 빠졌습니다. Diff에는 동일한 위험이 남아 있습니다.

- 부적절한 수정: `코드를 단순화하고 안정성을 높였습니다.`
- 적절한 수정: `운영 설정의 기본값을 변경했습니다. 이미 반영된 설정을 되돌리려면 환경별 설정 값을 복원해야 하므로 롤백 절차를 확인해야 합니다.`
- **판단/반례:** 본문을 짧게 만들기 전후에 중요 계약, 위험과 검증하지 못한 범위를 대조합니다. 위험이 실제로 해결되었고 증거가 확보되었다면 해결된 상태에 맞게 설명을 변경할 수 있습니다.

## 사례를 참고하기 전에 확인할 것

- 각 사례에는 `문제 유형 → 원인 → 수정 → 재확인 조건`의 관계가 드러나야 합니다.
- 비슷한 문제를 다른 변경 유형에서도 찾을 수 있어야 합니다.
- 예시 문구는 **실제 PR의 사실을 확인한 뒤에만** 사용해야 합니다.
