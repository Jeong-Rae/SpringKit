# PR 작업 절차

이 절차는 프로그래밍 언어, 빌드 시스템, 브랜치 전략과 관계없이 적용합니다. 저장소의 지침과 PR 템플릿을 우선합니다.

## PR 생성

1. 작업 트리와 현재 브랜치의 상태를 확인합니다.

   ```bash
   rtk git status --short
   rtk git branch --show-current
   rtk git diff -- <paths>
   ```

   요청과 관계없는 변경은 보존하고, 작업 범위는 요청받은 변경으로 한정합니다.

2. 해당 저장소의 지침을 읽습니다. Git을 변경하기 전에 브랜치 이름, 대상 브랜치, 커밋 형식, 검증 명령, 게시 방식, PR 상태 및 작업 권한의 범위를 확인합니다.

3. 저장소에서 요구하는 절차에 따라 작업 브랜치를 생성하거나 기존 브랜치로 이동합니다. 별도 절차가 없다면 저장소의 브랜치 명명 관례와 일반 Git 명령을 따릅니다.

4. 변경 사항을 검증할 수 있는 가장 좁은 범위의 검사를 실행합니다. 특정 언어나 빌드 도구를 가정하지 않고 저장소에서 정한 테스트, 린트, 빌드 또는 문서 검사를 사용합니다. 검증을 마치면 관련 파일만 스테이징하고 커밋합니다.

   ```bash
   rtk git add <paths>
   rtk git diff --cached --check
   rtk git commit -m "<repository-compliant title>"
   ```

5. PR 본문을 작성하기 전에 대상 저장소의 PR 템플릿을 찾습니다. 저장소 루트, `.github/`, `docs/`의 `PULL_REQUEST_TEMPLATE.md`와 `.github/PULL_REQUEST_TEMPLATE/`의 Markdown 템플릿 등 GitHub의 일반적인 위치를 확인합니다. 저장소에 템플릿 구성이나 선택 지침이 있다면 이를 따릅니다. 템플릿이 여러 개라면 이번 변경에 맞는 템플릿을 선택합니다.

   [pr-reviewer-guide.md](pr-reviewer-guide.md)와 [pr-description.md](pr-description.md)를 끝까지 읽고, 모든 PR 본문에 필수 설명·제외 사항·검토 기준·작성 규칙을 적용합니다.

   적용 가능한 저장소 템플릿이 있다면 스킬에 포함된 기본 구성 대신 해당 템플릿을 사용합니다. 템플릿의 섹션 구조를 유지하고, 필수 질문에는 확인된 변경 내용을 작성하며, 명시된 본문 요건을 충족합니다. 템플릿 요건과 일반적인 본문 작성 지침이 충돌하면 템플릿을 우선하고, 양립할 수 있는 지침은 계속 적용합니다.

   적용 가능한 템플릿이 없다면 스킬의 기본 구성을 사용합니다. PR 제목, 푸터, 브랜치, 게시 및 권한에 관해서는 저장소 지침을 따릅니다. 작성한 PR 본문 전체를 임시 Markdown 파일에 저장합니다.

6. 저장소에서 지정한 명령이나 스크립트로 변경을 게시합니다. 별도 절차가 없다면 브랜치를 푸시한 뒤 초안 PR을 생성합니다.

   ```bash
   rtk git push -u origin <branch>
   rtk gh pr create --draft --base <base> --title "<title>" --body-file <path>
   ```

   PR은 저장소에서 요구하는 상태로 유지합니다. 초안 해제, 병합, 배포와 같은 후속 작업까지 현재 요청의 권한이 확대된 것으로 간주하지 않습니다.

## PR 게시 실패 후 복구

재시도하기 전에 브랜치와 PR의 상태를 확인합니다.

```bash
rtk git status --short --branch
rtk gh pr view <branch> --json url,isDraft,title,baseRefName,state
```

로컬과 원격에서 완료된 단계와 실패한 명령을 구분해 보고합니다. 재시도해도 PR이 중복 생성되지 않는다는 사실을 확인한 뒤에만 다시 실행합니다. 인증에 실패했다면 사용자에게 인증 복구를 요청합니다.

## 리뷰 반영

PR의 Diff, 검사 결과 및 리뷰 의견을 확인합니다. 요청받은 범위에서만 수정하고 관련 검증을 실행한 뒤 커밋합니다. 저장소에서 정한 갱신 절차로 게시하며, 별도 절차가 없다면 현재 브랜치를 푸시합니다. 게시 후에는 승인 상태와 CI 결과를 다시 확인합니다.
