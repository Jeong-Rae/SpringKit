# 문제 유형, Must Not 확정 조건, 수정 방법

## 판정 원칙

표현의 유무만으로 위반을 확정하지 않는다. `Must Not` 위반은 최종 Diff와 문맥을 대조해 근거가 확인된 경우에만 `FAIL`로 판단한다. `Agent`, 테스트, 명령어 또는 숫자가 등장했다는 이유만으로 위반으로 분류하지 않는다. 해당 PR에 적용되지 않는 규칙은 `NOT_APPLICABLE`로 기록하고, 수정 전후에 중요한 정보가 유지됐는지 확인한다.

| ID | Must Not: 위반 확정 조건 | 검토 예외와 확인 방법 | 문제 → 해결방안 |
| --- | --- | --- | --- |
| PRC-001 | PR 설명이 리뷰어의 판단에 도움이 되지 않는 실행 기록이나 도구 사용 내역으로 채워짐 | 작업 도구 자체가 설계 근거/재현에 필수이면 예외 | 실행 기록은 따로 남기고 실제 변경의 영향을 설명 |
| PRC-002 | 의미 있는 변화 대신 수정 파일/커밋 목록이 핵심 설명을 대체함 | 파일 간 대응 자체가 중요한 큰 변경은 짧은 표 가능 | 파일별 변경을 계약, 책임, 동작의 변화로 나눠 설명 |
| PRC-003 | 후속 수정/검토 이력이 시간순으로 누적되어 최종 상태를 알 수 없음 | 이력이 실제 호환성 판단 근거이면 요약 유지 | 최신 Diff를 기준으로 최종 상태, 이유, 남은 쟁점만 재작성 |
| PRC-004 | 중요한 API/DB/권한/정책 변경이 최종 Diff에 있으나 PR 본문에서 빠짐 | 내부 구현 세부 사항은 보통 생략 가능 | 모든 중요 변경을 서브헤딩/표에 매핑하고 영향 설명 |
| PRC-005 | 변경된 주요 설계 선택이 있으나 문제/이유/대안 비용이 전혀 없어 판단 불가능 | 변경이 자명한 작은 수정은 별도 대안 분석 불필요 | 구체적 기존 문제 → 선택 → 이유/비용 연결 |
| PRC-006 | 테스트 생성/명령/해시 비교 등을 실행 성공 또는 기능 검증의 증거로 단정 | 관련 실행 로그와 기대 조건의 근거가 있으면 정확히 기록 | 확인된 주장에 맞춰 검증 범위를 좁히고 미확인 명시 |
| PRC-007 | 호환성/데이터 손실/운영 위험을 알고도 본문에서 숨김 | 해당 영향이 실제로 없다고 근거가 있으면 생략 가능 | 위험을 첫 부분과 영향 섹션에 놓고 결정 근거 제시 |
| PRC-008 | 검증이 수행되지 않았는데 수행했다고 표시하거나 중요한 실패를 누락 | 단순 CI 결과는 저장소 템플릿이 요구하지 않을 때 생략 가능 | 실행 사실/결과/확인하지 못한 부분을 구분 |
| PRC-009 | 문구 윤문과 `Must`/`Must Not`/`Should` 등 규범적 변경을 동등한 것으로 표시 | 규범적 강도가 실제로 변경되지 않았다면 사소한 윤문으로 분류 | 신규/변경 규칙을 독립 설명하고 적용 범위/강도 검토 |
| PRC-010 | 한 문단에 구조/API/저장소/배포/검증 등 독립된 판단 단위가 섞여 핵심을 찾기 어려움 | 작은 PR에서 한 문단이 명확하면 적용 제외 | 의미별 `###` 서브헤딩과 짧은 문단으로 재구성 |
| PRC-011 | 기존 문제나 용어 설명 없이 설계 결론/약어를 연속 제시해 독자가 의존 관계를 추론해야 함 | 팀 용어집과 PR 자체의 충분한 맥락 링크가 있으면 예외 | 먼저 문제/핵심 개념을 설명하고 이후 구조를 표/관계도로 전달 |
| PRC-012 | 복잡한 전후 구조/책임/호출 관계를 긴 나열 문장으로만 제공해 리뷰 판단이 어려워짐 | 표/도표를 추가해도 이해가 나아지지 않는 단순 변경은 예외 | 비교는 Markdown 표, 흐름/의존 관계는 확인된 Mermaid로 나타냄 |
| PRC-013 | 핵심적인 호환성 중단/이력 단절을 기술 상세 뒤에 배치하여 독자가 쉽게 놓침 | 중요도가 낮은 제한 사항은 뒤에 둘 수 있음 | 변경 요약에서 먼저 명시하고 영향 섹션에서 상세화 |
| PRC-014 | 본문 재작성 과정에서 검증 실패/중요 제약/계약/리뷰 요청이 사라짐 | 중복 표현 제거 및 실제 해결된 위험 삭제는 가능 | 수정 전후 중요 사실을 Diff에 대조하고 누락 복원 |

## 문제를 고치는 절차

1. 위반이 의심되는 문장 또는 문단을 원문 위치/관련 Diff와 함께 식별한다.
2. **리뷰어의 판단에 필요한 정보**와 단순 실행 로그를 분리한다.
3. `문제 → 영향 → 선택 및 근거 → 남는 불확실성`으로 내용을 다시 조직한다.
4. 관련 항목이 둘 이상이면 서브헤딩을 만든다. 비교가 필요한 데이터는 표, 흐름/관계는 다이어그램을 선택한다.
5. 수정을 통해 기존 계약/위험/검증 내용이 없어지지 않았는지 Diff와 다시 대조한다.
6. 문제별 `PASS`/`FAIL`/`NEEDS_REVIEW`/`NOT_APPLICABLE`을 근거와 함께 갱신한다.

## 자동 점검의 한계

- `PRC-010`의 긴 무제목 구간과 문단 길이는 **경고 후보**로는 기계 탐지할 수 있다. 구조가 실제로 필요한지는 의미 판단이 필요하다.
- `PRC-012`는 표/Mermaid의 부재만으로 위반이 되지 않는다. 비교/흐름 설명의 복잡성과 정보 손실을 실제로 확인해야 한다.
- `PRC-004`/`PRC-007`은 최종 Diff와의 비교가 필요하므로 Markdown 문자열 검사만으로 확인할 수 없다.
- 작성 중 표시가 남으면 자동으로 찾을 수 있지만, 위반의 심각도는 저장소 템플릿/사용자 요청에 따라 다르게 평가한다.
