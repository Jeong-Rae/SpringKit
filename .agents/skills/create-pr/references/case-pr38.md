# SpringKit PR #38: 주제별로 나누고 그림으로 설명하기

사례: [Agent Guidebook BC/Slice 리팩터링](https://github.com/Jeong-Rae/SpringKit/pull/38). 2026년 11월 6일 확인한 PR 본문과 최종 Diff를 바탕으로 설명을 다시 구성한 예시다. 확인하지 않은 변경 이유나 테스트 성공 여부는 덧붙이지 않는다.

## 기존 설명의 문제

- 첫 문단부터 `BC`, `Slice`, `domain`, `search`, `provision`이 등장한다. 기존 구조가 실제로 어떤 실패나 비용을 유발했는지는 설명하지 않는다.
- 다음 문단에 Port, Repository, UnitOfWork, SQLite, Codex, Factory, Application이 모여 있다. 독자는 어느 요소가 무엇을 맡고 의존하는지 직접 추론해야 한다.
- 공개 API 호환성 중단, DB 이력 단절 같은 중요한 변경이 패키지 배치 설명보다 뒤에 있다.
- 변경 파일 149개 중 기술 문서 16개가 삭제됐다. 기존 계약이 다른 문서나 코드에 남아 있는지 확인해야 한다.
- CI 비활성화는 밝히지만, PR 본문만으로 로컬 테스트의 실행 결과를 판정하기 어렵다.

## 권장 시작 단락

`Agent Guidebook`의 검색/지침 제공 기능이 여러 패키지에 분산되어 있습니다. 이번 PR에서는 하나의 Bounded Context 안에 `search`와 `provision`을 구분하고, 공통 검색 규칙은 `domain`으로 옮겨 책임 경계를 재구성합니다. **기존 호출 API와 SQLite 이력에 대한 호환성은 제공하지 않습니다.**

위 내용은 확인된 구조 변경과 명시된 비호환성을 요약한다. 기존 패키지 분산이 실제 어떤 유지보수 문제를 낳았는지는 추가 근거가 확보되면 첫 문단에 반영한다.

## 권장 서브헤딩

### 도메인과 기능별 책임

`domain`, `search`, `provision`의 역할을 한 문장으로 소개하고, 각 책임의 이전/변경 후를 비교표로 보여 준다. `search`와 `provision`을 분리한 실제 이유를 덧붙인다.

### Slice 간 협력과 기술 구현

`provision`이 `SearchGuidelines`에 의존하는 관계, 파일 시스템과 SQLite Adapter를 연결하는 Factory 위치를 **실제 코드에서 확인한 방향**으로 Mermaid 그래프 한 장에 설명한다.

### 공개 API와 실행 진입점

기존 호출 방법과 새 호출 방법을 간단한 표로 비교한다. 기존 소스와 바이너리와 호환되지 않는다는 점을 명확히 알린다.

### 이력 저장의 변경과 데이터 영향

Exposed에 트랜잭션을 위임하는 선택, 기존 테이블 대신 `provision` 테이블을 사용하는 변화, 이전 이력을 재사용하지 않고 마이그레이션을 제공하지 않는 선택을 구분한다. 실제 제공 동작에 미칠 위험과 수용 근거는 별도 검토가 필요하다.

### 검증 범위와 삭제한 문서

변경된 테스트가 무엇을 확인하도록 작성되었는지와 **실제로 실행에 성공했는지**를 구분한다. 삭제된 계약/검증 문서 중 현재 유효한 계약이 코드/테스트/README에 남았는지 점검한다. CI가 비활성화됐다는 사실도 설명한다.

### 검토 요청

설계 책임 경계, 호환성 단절, 기존 DB 이력 처리, 트랜잭션과 동시성 경계를 검토 요청에 연결한다.

## 이 예시의 교훈

더 많은 표를 넣는 것 자체가 목적은 아니다. **독자가 이해해야 할 논점별로 구획을 나누고, 관계와 대비를 시각화하며, 변경의 이유와 위험을 명시하는 것**이 목적이다. 긴 문단을 나누는 것만으로는 충분하지 않다.
