# PR Creator

## 좋은 PR이 지향하는 상태

좋은 PR은 작업 수행자의 성과 보고서가 아니라, **다른 개발자가 변경의 필요성, 설계 선택, 계약의 변화와 위험을 독립적으로 판단할 수 있는 검토 자료**다. 작성자는 독자가 자신의 작업 이력을 모른다는 전제로 설명한다. 리뷰어가 Diff를 살피기 전에 '어떤 문제 → 어떤 선택 → 어떤 결과 → 어떤 확인과 불확실성 → 무엇을 판단할지'의 인과관계를 파악할 수 있게 한다.

읽는 사람의 주의력을 설계 자원으로 취급한다. 정보가 많다는 이유로 좋은 PR이 되지 않는다. **핵심 결정은 앞에, 관계는 표·다이어그램으로, 세부 구현은 근거 링크로** 배치한다. 중요하고 위험한 정보를 간결함을 이유로 삭제하지 않는다.

문서의 구조는 독자를 위해 구성한다. 기존 코드의 명명·패키지에 익숙한 작성자의 머릿속 순서를 독자에게 강요하지 않는다.

## 작성·검토 절차

1. **저장소 계약 수집**: `AGENTS.md`, `CONTRIBUTING.md`, PR 템플릿, 이슈, 제목·브랜치·권한 지침을 확인한다. 저장소의 필수 형식과 권한을 우선한다. 권한을 얻지 않고 PR을 게시, Draft 해제, 병합하지 않는다.
2. **최종 변경의 의미 분류**: 최종 Diff와 공개 계약·테스트·설정·문서를 확인한다. 실제 동작 변화, API·DB 계약, 운영 정책, 설계 책임, 규범적 지침, 순수 문구 수정을 분리한다. 모든 중요 변경을 본문의 의미 단위에 대응한다.
3. **독자에게 필요한 사전 맥락 식별**: 기존 문제와 결과, 바뀐 이유, 핵심 결정과 대안, 호환성·실패·마이그레이션의 영향을 확인한다. 근거 없는 동기를 추정하지 않는다.
4. **정보 우선순위와 표현 방법 선택**: 첫 단락에 한두 문장으로 문제와 핵심 변경을 설명한다. 그 뒤 의미별 서브헤딩을 구성한다. 비교가 중요하면 표, 호출·의존·분기 관계가 중요하면 다이어그램을 사용한다. 시각 자료 사용 조건은 [visual-structure.md](references/visual-structure.md)를 따른다.
5. **검증을 정확하게 서술**: 실제로 실행된 검사의 결과와 보장 범위를 확인한다. 테스트 작성, CI 설정, CI 성공, 로컬 실행, 통합 검증은 서로 다른 사실이다. 미실시 항목·실패·한계를 숨기지 않는다.
6. **리뷰 요청을 특정**: 검토할 계약, 구조, 실패 경계, 데이터 이행, 정책 판단을 위치와 함께 지정한다. 작은 수정에서 실제 쟁점이 없으면 억지로 만들지 않는다.
7. **진단 → 수정 → 재점검**: [index.md](references/index.md)의 문제 유형을 적용하고 [problem-catalog.md](references/problem-catalog.md)에서 원인·수정·예외를 확인한다. 위반이 확정된 항목은 수정하고, 미확인 항목은 별도로 표시한다. [rubric.md](references/rubric.md)의 각 축을 평가한다.
8. **최종 일치성 확인**: 본문·도표·표·링크가 최종 Diff, 공개 계약, 실제 검증 결과와 일치하는지 확인한다. 저장소 템플릿 충족 및 권한 경계를 다시 확인한 뒤 사용자가 요청한 산출물만 전달하거나 승인받은 작업을 실행한다.

## 본문 구성

저장소 템플릿이 없을 때는 [assets/pr-template.md](assets/pr-template.md)를 기반으로 변경 규모에 따라 축약한다.

- **왜 바꾸는가**: 기존의 구체적인 문제, 재현 조건 또는 설계상의 비용. 문서의 목적을 '코드 품질 향상'처럼 빈 표현으로 채우지 않는다.
- **핵심 변경**: 사용자·API·도메인 동작, 권한, 데이터 스키마 또는 규칙의 실제 차이. 파일 목록을 핵심 설명으로 대체하지 않는다.
- **설계 선택**: 중요한 책임 경계·대안·트레이드오프. 코드를 읽어도 알기 어려운 이유를 먼저 설명한다.
- **영향과 제약**: 호환성, 기존 데이터, 배포·롤백, 누락된 마이그레이션, 운영·보안 영향. 중요하다면 첫 단락에서도 알린다.
- **검증**: 명령 목록이 아니라 확인한 계약과 결과, 실행 여부, 잔여 미확인 상태.
- **검토 요청**: 리뷰어가 실제로 판단할 부분을 간결하게 연결한다.

**하나의 긴 '변경 내용' 문단에 모든 개념을 넣지 않는다.** 설계·공개 API·DB·실행 경계·테스트·운영 영향을 서로 다른 주제로 다루면 의미별 `###` 서브헤딩을 사용한다. 새 서브헤딩 앞에 읽는 이유가 드러나는 제목을 둔다. 길이 숫자는 신호일 뿐이며 단락의 실제 의미를 우선한다.

## 표·다이어그램 선택

- **전후 상태·계약·책임 비교**가 두 가지 이상이면 Markdown 비교표를 우선 검토한다. 열은 `대상 | 이전 | 변경 후 | 영향/이유`처럼 직접 비교되는 속성만 둔다.
- **객체·모듈 간 의존, 호출 순서, 트랜잭션 경계, 실패 분기**를 설명한다면 Mermaid `flowchart`, `sequenceDiagram`의 사용을 우선 검토한다. `BC`, `Slice`, `Factory`, `Repository`를 텍스트로 나열하는 대신 관계를 보여 준다.
- **선택 이유와 예외**는 짧은 산문으로 설명한다. 표나 다이어그램이 그 판단 이유를 대신한다고 가정하지 않는다.
- **작은 PR** 또는 관계가 한두 문장으로 충분한 경우 시각 자료를 강제하지 않는다. 모든 시각 자료는 PR의 사실에 근거하고, 본문에서 의미를 한 문장으로 요약한다. 렌더링 결과와 읽기 순서를 확인한다.
- 시각 자료에 민감 정보, 확인하지 않은 구조, 설명되지 않은 약어를 넣지 않는다. GitHub에서 Mermaid 렌더링이 어려운 환경이면 텍스트 관계 설명으로 대체한다.

상세 기준과 before/after 예시는 [visual-structure.md](references/visual-structure.md), PR #38 재구성 예시는 [case-pr38.md](references/case-pr38.md)를 참조한다.

## 한국어 문체

- 변경 대상, 조건과 결과를 주어로 삼는다. `검토했다`, `도구를 적용했다`, `확인했다`는 수행 기록이 아닌 실제 증거를 전달할 필요가 있을 때만 쓴다.
- 규범적 의미를 구별한다. `Must`, `Must Not`, `Should`의 강도와 예외·적용 범위를 임의로 바꾸지 않는다.
- 코드 식별자, 정확한 기술 용어는 그대로 사용하되 처음 등장하는 약어와 내부 개념은 간단히 풀어 쓴다.
- 사실, 작성 의도, 기대 효과, 실제 검증, 미확인을 분리한다. 근거가 없는 `동일`, `안전`, `검증 완료`, `영향 없음`을 단정하지 않는다.
- 중요한 내용은 제목과 짧은 문단으로 구분하고, 한 문단에는 하나의 논점만 둔다. 요약과 같은 내용을 표 아래에서 다시 길게 반복하지 않는다.

## Must Not의 적용 원칙

[problem-catalog.md](references/problem-catalog.md)에 정리된 `PRC-001`~`PRC-014`를 적용한다. `Must Not` 판정은 **금칙어 등장, 문단 길이, 도표 유무만으로 확정하지 않는다**. 최종 Diff·저장소 정책·본문과 증거를 대조해서 위반 조건을 충족할 때 `FAIL`로 판정한다. 단순 패턴 일치는 `NEEDS_REVIEW`로 남긴다. 중요한 위반 하나를 높은 루브릭 총점으로 상쇄하지 않는다.

- `FAIL`: 근거와 위반 조건이 확인됨. 수정 후 재평가한다.
- `NEEDS_REVIEW`: 문맥·실행 근거·대안 확인이 필요함.
- `PASS`: 해당 축에서 위반이 없음을 근거로 판단함.
- `NOT_APPLICABLE`: 명확한 적용 제외 이유가 있음.

표·다이어그램의 실질적인 필요성도 동일하게 판단한다. 큰 PR이라도 호출 관계나 비교 대상이 없으면 '다이어그램 없음'으로 실패 처리하지 않는다. 반대로 서로 다른 추상화 수준의 정보가 긴 문단에 얽혀 있어 독자가 관계를 추론해야 한다면 구조 보완을 요구한다.

## 자동 점검과 수정

`scripts/check_pr.py`는 PR Markdown 문서의 기계적 신호를 보고한다. 이 도구는 긴 무제목 구간, 긴 문단, 표·Mermaid 존재 여부, 미해결 플레이스홀더를 확인한다. 경고는 개선 후보이며 모든 경고가 Must Not 위반은 아니다. 사용 시 `python scripts/check_pr.py /path/to/pr.md`.

문제가 발견되면 단순히 내용을 삭제하지 말고 `문제 → 리뷰어에게 발생하는 영향 → 필요한 정보·구조적 표현 → 수정 → 중요 계약 보존 확인`의 순서로 고친다. 별도 운용자 보고에 유용한 도구 이력은 PR 본문에서 분리한다.
