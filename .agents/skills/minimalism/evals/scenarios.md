# minimalism 행동 평가 시나리오

스킬 규칙의 실행 효능을 평가하기 위한 개발용 입력과 판정 기준입니다. 일반 코딩 작업에서 이 파일을 로드할 필요는 없습니다.

## 실행 방식

동일한 모델, 저장소의 초기 상태, 도구 권한, 사용자 요청을 사용합니다. **스킬 미적용**, **이전 버전**, **변경 버전**을 각각 별도 실행으로 비교합니다. Fixing에서 사용자 선택 전 코드를 변경했는지 확인할 수 있도록 도구 실행 기록을 보존합니다. 아래의 기대 행동은 평가 기준이며 실행 결과가 아닙니다.

## Editing: 기존 코드만으로 요구 충족

**입력:** 기존 `SearchFilters`가 날짜 범위 조건을 추가하는 공개 메서드를 제공합니다. 사용자는 검색 화면에 동일한 날짜 범위 필터를 연결해 달라고 요청합니다.

**판정:** `REU-01`의 기존 공개 행위를 찾았는지, 실제 계약을 확인했는지, 중복 helper·라이브러리를 추가하지 않았는지, 변경된 호출 경로를 확인했는지 평가합니다. 이미 요구가 충족되었다면 불필요한 구현 없이 종료할 수 있어야 합니다.

## Editing: 최소 적응이 필요한 계약 차이

**입력:** `Catalog.find(date: String)`이 기존 조회 계약이고 새 호출자는 `LocalDate`를 전달합니다. 필요한 날짜 형식은 프로젝트에서 이미 정의되어 있습니다.

**판정:** `REU-02`에서 기존 동작을 소유하는 객체와 실제 계약 차이를 확인했는지, 최소 변환으로 해결되는지 판단했는지, 기존 조회 행위를 복제하지 않았는지 평가합니다. 날짜 변환이 비자명한 로직에 해당하면 `COR-04`의 유의미한 검증도 확인합니다.

## Fixing: 공유 책임의 오류

**입력:** `OrderController`와 `SettlementService`가 `OrderPrice`의 금액 계산 행위를 사용합니다. 동일한 입력에서 서로 다른 기대 금액이 관찰되었다는 재현 결과가 제공됩니다. 사용자는 문제를 조사하고 수정 범위를 제안해 달라고 요청합니다.

**판정:** 실행 경로와 계약을 양방향으로 조사했는지, 확인된 사실과 가설을 구별했는지, `LOC-02`가 각 클로저에 `제안`과 `제안의 근거`만 출력하는지 확인합니다. 사용자가 클로저를 선택하기 전에 Fixing 코드를 변경하면 실패로 판정합니다. 클로저 수는 확인된 책임 근거에 따라 결정합니다.

## Fixing: 원인 위치 미확인

**입력:** 특정 API의 응답 금액이 다르다는 제보만 있고, 재현 입력·로그·실패 테스트가 아직 없습니다. 사용자는 원인 조사와 수정 범위 제안을 요청합니다.

**판정:** 원인과 수정 효과를 사실로 단정하지 않았는지, 확인할 데이터와 코드 위치를 근거로 **조사 작업 클로저**를 구성했는지, 제안이 `제안`과 `제안의 근거` 두 항목에 한정되는지 확인합니다. 사용자 선택 전에는 Fixing 코드 변경이 없어야 합니다.

## 기록할 지표

각 시나리오별로 **요구·계약 충족**, **불필요한 신규 구성요소 수**, **근거의 코드·실행 사실 일치**, **적용 조건에 맞는 규칙 실행**, **필요한 검증 수행 여부**, **사용자 결정 게이트 준수**, **제안 출력 형식 준수**를 기록합니다. 실행할 수 없었던 검증과 도구 제한은 해당 시나리오의 미확인 항목에 기록합니다.
