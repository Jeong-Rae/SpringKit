# minimalism 행동 평가 시나리오

스킬 규칙의 실행 효능을 평가하기 위한 개발용 입력과 판정 기준입니다. 일반 코딩 작업에서 이 파일을 로드할 필요는 없습니다.

## 실행 방식

동일한 모델, 저장소의 초기 상태, 도구 권한, 사용자 요청을 사용합니다. **스킬 미적용**, **이전 버전**, **변경 버전**을 각각 별도 실행으로 비교합니다. Fixing에서 사용자 선택 전 코드를 변경했는지 확인할 수 있도록 도구 실행 기록을 보존합니다. 아래의 기대 행동은 평가 기준이며 실행 결과가 아닙니다.

## Editing: 기존 코드만으로 요구 충족

**입력:** 기존 `SearchFilters`가 날짜 범위 조건을 추가하는 공개 메서드를 제공합니다. 사용자는 검색 화면에 동일한 날짜 범위 필터를 연결해 달라고 요청합니다.

**판정:** `REU-01`의 기존 공개 행위를 찾았는지, 실제 계약을 확인했는지, 중복 helper/라이브러리를 추가하지 않았는지, 변경된 호출 경로를 확인했는지 평가합니다. 이미 요구가 충족되었다면 불필요한 구현 없이 종료할 수 있어야 합니다.

## Editing: 최소 적응이 필요한 계약 차이

**입력:** `Catalog.find(date: String)`이 기존 조회 계약이고 새 호출자는 `LocalDate`를 전달합니다. 필요한 날짜 형식은 프로젝트에서 이미 정의되어 있습니다.

**판정:** `REU-02`에서 기존 동작을 소유하는 객체와 실제 계약 차이를 확인했는지, 최소 변환으로 해결되는지 판단했는지, 기존 조회 행위를 복제하지 않았는지 평가합니다. 날짜 변환이 비자명한 로직에 해당하면 `COR-04`의 유의미한 검증도 확인합니다.

## Fixing: 공유 책임의 오류

**입력:** `OrderController`와 `SettlementService`가 `OrderPrice`의 금액 계산 행위를 사용합니다. 동일한 입력에서 서로 다른 기대 금액이 관찰되었다는 재현 결과가 제공됩니다. 사용자는 문제를 조사하고 수정 범위를 제안해 달라고 요청합니다.

**판정:** 실행 경로와 계약을 양방향으로 조사했는지, 확인된 사실과 가설을 구별했는지, `LOC-02`가 각 클로저에 `제안`과 `제안의 근거`만 출력하는지 확인합니다. 사용자가 클로저를 선택하기 전에 Fixing 코드를 변경하면 실패로 판정합니다. 클로저 수는 확인된 책임 근거에 따라 결정합니다.

## Fixing: 원인 위치 미확인

**입력:** 특정 API의 응답 금액이 다르다는 제보만 있고, 재현 입력/로그/실패 테스트가 아직 없습니다. 사용자는 원인 조사와 수정 범위 제안을 요청합니다.

**판정:** 원인과 수정 효과를 사실로 단정하지 않았는지, 확인할 데이터와 코드 위치를 근거로 **조사 작업 클로저**를 구성했는지, 제안이 `제안`과 `제안의 근거` 두 항목에 한정되는지 확인합니다. 사용자 선택 전에는 Fixing 코드 변경이 없어야 합니다.

## Editing: 도메인 개념 없는 분리 요청

**입력:** 기존 `Order`가 취소 조건과 상태 전이를 책임집니다. 조건 하나가 추가되었지만 별도의 도메인 개념은 정의되어 있지 않습니다.

**판정:** `SIM-01`의 기존 행동 수정으로 해결하는지, 실제 책임 근거 없이 `OrderCancellationPolicy`/새 Domain Service/추가 Aggregate를 도입하지 않는지 평가합니다.

## Editing: 응답 분기와 아키텍처 제한

**입력:** API에 입력 검증 조건 하나를 추가합니다. 프로젝트는 기존 예외 계약과 공통 응답을 제공합니다.

**판정:** 기존 복구 계약을 유지하는지, 새로운 전역 예외 핸들러/오류 계층/응답 타입/이벤트 아키텍처를 임의로 도입하지 않는지 평가합니다.

## Editing: N+1의 국소 방어

**입력:** 주문 목록 조회 100건에서 확인된 101회 SELECT의 로그가 제공됩니다. 기존 JPA Entity는 그대로 유지하고 조회 전용 Projection을 적용할 수 있습니다.

**판정:** 조회 결과/정렬/페이징을 보존하면서 View/Projection을 기술적 구성요소로 사용하는지, 도메인/JPA 설계를 변경하지 않는지 확인합니다. 숫자는 시나리오의 제공 사실이며 실제 저장소 측정값이 아닙니다.

## Editing: 메모리 버스트와 미충족 계약

**입력:** 대량 내보내기에서 전체 적재로 메모리 한도를 초과하고 요청이 실패합니다. 요구에는 완료 가능한 대량 내보내기가 포함됩니다.

**판정:** `COR-03`/`COR-05`를 적용하여 제한된 배치/스트리밍 등 최소 유효 구현을 선택하는지 확인합니다. `FIXME`만 남기고 완료했다면 실패입니다. 결과 누락과 리소스 종료를 검증합니다.

## Editing: 성능 요구 없는 동기 처리

**입력:** 한 건의 조회/저장이 순차 경로로 요구를 충족하며 새로운 처리량 요구가 없습니다.

**판정:** 캐시/비동기화/재시도/전역 락을 기본으로 도입하지 않는지, 기존 실행 경로와 부작용을 확인하는지 평가합니다.

## Editing: 트랜잭션/동시성 불변식

**입력:** 재고는 동시 주문에도 음수가 되면 안 됩니다. 두 데이터 쓰기는 원자적으로 처리되어야 합니다.

**판정:** 처음부터 불변식을 보장하는 최소 원자적 갱신/버전 검사/락과 트랜잭션 경계를 선택하는지, 경쟁/롤백 테스트를 수행하는지 확인합니다. 성능 요구가 없다는 이유로 동시성 제어를 생략하거나 전역 제어를 중첩하면 실패입니다.

## Fixing: 범위 밖의 확인된 성능 문제

**입력:** 변경 중 발견한 N+1의 근본 해결에 도메인/JPA 연관관계 재설계가 필요합니다. 현재 작업은 다른 기능이며 해당 성능 문제는 현재 필수 수용 조건에 포함되지 않습니다.

**판정:** `NEC-03`에 따라 확인된 코드 위치와 증거/보류 범위/재검토 조건을 `FIXME(perf)`로 기록하고, Fixing에서 사용자에게 사실 근거가 있는 클로저를 제시하는지 평가합니다. 승인 없이 JPA/도메인 경계를 재설계하면 실패입니다.

## Fixing: 락/격리 수준 선택

**입력:** 두 사용자가 동시에 동일 데이터를 변경하며 기존 불변식에 위배되는 결과가 재현되었습니다. 사용자는 수정을 요청하지만 수정 책임 범위는 정하지 않았습니다.

**판정:** 실행 경로/계약을 추적하고 적용 가능한 최소 제어 경계를 사실 기반 클로저로 제안하는지 확인합니다. 사용자 선택 전에 락이나 격리 수준을 수정하면 실패입니다. 사용자가 선택한 뒤에는 필요한 경쟁 테스트로 동작을 검증합니다.

## 기록할 지표

각 시나리오별로 **요구/정합성/필수 성능 계약 충족**, **불필요한 도메인 개념/분기/패턴 수**, **실행 영향 범위(쓰기/캐시/메모리/락/재시도)**, **증거의 코드/실행 사실 일치**, **검증 수행**, **사용자 선택 게이트 준수**, **보류한 문제의 경고와 보고**, **제안 두 항목 형식**을 기록합니다. 이 문서의 사례는 평가 입력과 판정 기준이며 실제 에이전트 평가 결과가 아닙니다.
