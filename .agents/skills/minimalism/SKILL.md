# Minimalism

## 목표와 기준

미니멀리즘의 시작점은 **현재 요구와 시스템 계약을 충족하는 최소 제어 수준**입니다. 코드 줄 수가 아니라 필요한 도메인 책임, 상태/응답 분기, 실행 순서, 부작용, 의존성과 변경 비용을 함께 최소화합니다. Bracketing은 이 유효한 시작점에서 실제 미충족 조건이 확인될 때만 제어 범위를 확장하는 방식입니다.

**최소 완결 해법**은 요구된 동작과 수용 조건을 만족하고, 책임 경계/호출자 계약/보안/데이터 보존/현재 운영 제약을 유지하면서 더 강한 제어나 새로운 구조를 요구하는 근거가 없는 해법입니다. 성능 목표가 없고 현재 운영 조건을 충족한다면, 처리량이 낮더라도 단순한 순차 실행과 기존 데이터 접근을 기본 후보로 삼습니다. 필수 정합성/원자성/동시성 계약은 처음부터 충족합니다.

**Rich Domain Model**에서는 실제 도메인 의미와 불변식을 가진 객체에 상태와 행위를 함께 둡니다. 독립적인 도메인 개념이 확인되지 않은 객체 분리, 새로운 패턴/아키텍처/예외 계층은 생성하지 않습니다. 성능 방어에 필요한 조회 전용 View/Projection은 기술적 구성요소로 다룹니다. **실행 영향 범위**는 쓰기, 외부 호출, 캐시, 메모리, 트랜잭션, 재시도, 락, 동시 실행과 실행 순서의 변화까지 포함합니다.

**작업 클로저(Closure)**는 하나의 수정 책임 경계와 그 변경을 독립적으로 검증하는 데 필요한 호출자/테스트/설정을 포함하는 작업 범위입니다. 프로그래밍 언어의 함수 클로저와 구별합니다. Fixing에서는 증상이 나타난 위치와 원인을 담당하는 책임 위치를 각각 조사하여 클로저를 구성합니다.

## 작업 분기

사용자가 스킬을 호출하면 작업 의도에 따라 하나의 주된 알고리즘을 실행합니다.

| 작업 | 적용 조건 | 알고리즘 |
| --- | --- | --- |
| **Editing** | 기능 추가, 요구된 동작 변경, 리팩터링/코드 정리 | A: 점진적 확장 탐색 |
| **Fixing** | 기존 동작이 계약/기대 결과와 다른 원인을 조사하고 수정 | C: 책임/클로저 탐색 |

하나의 요청에 두 작업이 섞여 있으면 해당 범위를 구분합니다. Editing으로 작성한 코드의 검증 실패는 Editing 탐색에서 수정합니다. 기존 코드의 별도 결함을 발견한 경우에는 Fixing으로 전환합니다. 분석/리뷰만 요청받았다면 코드를 수정하지 않고 관련 규칙에 따라 확인한 사실을 전달합니다.

## Editing: A 점진적 확장 탐색

**점진적 확장 탐색**은 요구를 충족할 가장 작은 후보부터 시작하여 **충족하지 못한 조건이 확인될 때만** 기능/책임/변경 범위를 확장하는 방법입니다. 후보가 수학적으로 단조롭게 정렬되었다고 가정하지 않습니다. 코드 줄 수보다 올바른 책임과 실제 계약의 충족을 우선합니다.

1. **요구 확인:** 수용 조건과 도메인 불변식, 기존 호출/실행 계약을 확인합니다. 트랜잭션 격리/동시성/락이 결과의 정확성에 필요한지 먼저 판단합니다. (`NEC-01`, 해당 시 `COR-01`~`COR-03`)
2. **최소 유효 후보:** 기존 동작부터 **직접 재사용 → 기존 책임 수정/최소 적응 → 표준/설치 기능 → 새 라이브러리 검토 → 최소 신규 구현** 순으로 탐색합니다. 각 후보가 필요한 정확성/원자성 및 실행 제어를 충족하는지 함께 확인합니다. (`REU-01`~`REU-04`, `SIM-01`~`SIM-02`, `COR-02`, `COR-05`)
3. **Bracketing:** 후보가 충족하지 못하는 실제 계약을 확인하고, 그 조건을 만족할 최소 책임/제어 범위로만 확장합니다. 독립된 도메인 개념, 추가 응답 분기, 패턴과 성능 최적화는 증거를 요구합니다. (`NEC-02`, `SIM-01`~`SIM-03`, `COR-05`)
4. **구현:** 선택된 도메인 책임과 실행 경계 안에서 행위를 구현하고 영향받는 호출자/테스트/설정을 반영합니다. 확인된 성능 문제는 도메인/JPA 재설계 없이 가능한 국소 대응을 검토합니다. (`SIM-01`~`SIM-04`, `COM-01`, `COR-03`~`COR-05`)
5. **검증/종료:** 필수 계약과 부작용, 실행 결과를 검증합니다. 미충족 조건이 있으면 해당 판단으로 돌아갑니다. 범위를 넘는 확인된 성능 개선은 정확한 코드 경고와 작업 결과에 기록하며, 필수 계약이 충족된 경우에만 완료를 선언합니다. (`COR-04`, `NEC-03`, `COM-02`)

예: 기존 검색 화면에 날짜 필터를 추가할 때 먼저 기존 입력 컴포넌트와 검색 계약을 확인합니다. 현재 계약으로 날짜 값 전달이 가능하면 이를 사용합니다. 실제 입력 계약의 차이가 확인되면 그 부분만 수정하거나 최소 변환 함수를 검토합니다.

## Fixing: C 책임/클로저 탐색

**양방향 책임 탐색**은 증상에서 실행 경로를 따라 원인 후보를 조사하고, 계약/불변식에서 실제 책임 위치를 역으로 추적하여 두 결과를 대조하는 방법입니다. 확인한 코드와 실행 증거를 바탕으로 수정 작업 클로저를 도출하며, **코드 수정에 앞서 사용자에게 제안**합니다.

1. **현상/증거 확인:** 기대 결과와 재현 입력, 테스트/쿼리 로그/메모리/락 등 필요한 실행 증거를 확보하고, 관찰 사실과 가설을 구분합니다. (`NEC-01`, `COR-03`~`COR-04`, `LOC-01`)
2. **양방향 위치 추적:** 증상에서 호출자/피호출자/데이터 및 부작용 경로를 조사하고, 계약/불변식에서 책임 객체와 최소 필수 제어 경계를 역추적합니다. (`LOC-01`, `SIM-01`, `COR-02`, `COR-05`)
3. **클로저 구성:** 확인된 책임과 쓰기/캐시/트랜잭션/동시성 영향 범위에서 독립적으로 검증 가능한 수정 또는 조사 클로저를 구성합니다. 도메인/JPA 재설계가 필요한 성능 문제는 기존 범위와 분리해 제시합니다. (`LOC-02`, `COR-05`, `COM-01`)
4. **사실 기반 제안:** 각 클로저에 **「제안」과 「제안의 근거」** 두 항목만 작성합니다. 첫 항목에는 수정/조사할 책임과 범위를, 둘째 항목에는 확인한 코드/호출 관계/재현 사실을 적습니다. 제안 단계에서는 사실만 전달하고 사용자에게 범위 선택을 맡깁니다. 비교 평가는 사용자가 별도로 요청할 때 수행합니다. ([원인/클로저 지침](references/location.md), `LOC-02`)
5. **사용자 선택:** 사용자가 클로저를 선택할 때까지 Fixing의 코드를 변경하지 않습니다. 이미 명시적으로 범위를 선택했다면 동일한 선택을 다시 요청하지 않습니다. 선택한 범위 안에서 Editing의 A 알고리즘을 적용합니다. (`LOC-02`, `REU-01`~`REU-04`)
6. **검증/경계 확인:** 선택된 클로저의 계약과 호출 경로를 검증합니다. 다른 책임 범위의 변경이 필요하다는 사실이 확인되면 해당 범위를 새 클로저로 제시하고 선택을 받은 뒤 수정합니다. (`COR-04`, `COM-01`, `COM-02`)

제안 예시는 [원인/클로저](references/location.md)에 있습니다. 실제 작업에서는 저장소의 코드와 관찰 결과로 확인한 내용만 근거로 사용합니다.

## 실행 제어의 경계

- **기능/정합성 계약:** 중복 차감 방지, 여러 쓰기의 원자성, 동시 수정 충돌과 같은 조건이 현재 기능에 필수라면 최초 구현부터 이를 충족하는 **최소 유효 제어**를 선택합니다. 전체 시스템에 락을 걸거나 격리 수준을 일괄 상향하지 않습니다. (`COR-02`, `COR-05`)
- **성능/자원 문제:** 확인된 N+1, 메모리 버스트, 오래 걸리는 트랜잭션, 캐시 문제는 현재 조회/실행 책임에서 가능한 국소 방어부터 검토합니다. View/Projection, 제한된 페이지/청크 처리 등은 도메인 변경 없이 적용할 수 있는 기술적 수단입니다. (`COR-03`, `COR-05`, `REU-02`)
- **범위 밖의 확인된 문제:** 도메인 또는 JPA Entity 재설계가 요구되고 현재 범위에 포함되지 않으면 정확한 위치에 `FIXME(perf)`와 관찰 증거/보류 범위/재검토 조건을 남기고 보고합니다. 현재 기능의 필수 조건이 충족되지 않는다면 완료로 판단하지 않고 별도 작업 클로저를 제안합니다. (`NEC-03`, `LOC-02`, `COM-02`)

## 규칙 적용 계약

**알고리즘은 판단 순서, 규칙은 판단 기준을 정의합니다.** 인덱스는 해당 시점에 실행할 코드를 찾는 표입니다. 참조 문서는 코드별 **적용 조건 → 수행 행동 → 판단 증거 → 다음 전이**를 정의합니다.

- **적용 조건:** 실제 작업/코드에서 조건을 확인할 때 활성화합니다. `공통`은 두 알고리즘에 적용하며, `Editing`은 Fixing의 클로저 선택 후 A를 실행하는 경우에도 적용합니다. 여러 조건이 적힌 규칙은 해당 조건 중 하나에 해당하면 활성화합니다.
- **수행 행동과 판단 증거:** 현재 단계에 필요한 행동을 수행하고, 코드/계약/테스트 등 확인 가능한 결과에 근거해 판단합니다. 증거가 부족하면 해당 조사/검증으로 돌아갑니다.
- **다음 전이:** 조건을 충족하면 다음 판단으로 진행하고, 미충족 조건이 있으면 관련 단계로 복귀합니다. 사용자 선택 게이트는 `LOC-02`에 따릅니다. 이 네 요소는 **에이전트의 내부 실행 계약**이며 사용자에게 매번 출력하는 체크리스트가 아닙니다.
- 해당 판단에 구체적인 지침이 필요할 때 관련 참조 파일만 읽습니다. **Fixing 클로저 구성/제안 전에는 반드시 [원인/클로저](references/location.md)의 `LOC-01`/`LOC-02`를 읽습니다.** 미확인 조건을 추측하여 적용하거나 무관한 참조를 일괄 로드하지 않습니다.
- 프로젝트 지침과 명시적 사용자 요구, 도메인 불변식, 호출자 계약, 보안/데이터 보존을 유지합니다. 성능 목표가 없다는 이유로 필수 정합성 제어를 생략하지 않습니다. 선택된 클로저의 경계를 넘어야 한다면 수정 전에 새로운 클로저를 제안합니다. 사용자가 제안만 요청한 경우에는 조사 결과와 확인된 근거를 전달하고 코드를 수정하지 않습니다.

## 완료 조건

**Editing:** 요청된 동작/필수 제어/관련 호출 경로와 부작용을 검증합니다. 확인된 성능 문제를 범위 밖에 보류한 경우에는 증거와 재검토 조건을 기록합니다. 필수 계약이 미충족이면 완료로 판단하지 않습니다.

**Fixing:** 클로저를 사용자에게 제시하고 선택된 범위에서만 변경과 검증을 수행합니다. 추가 책임 범위를 임의로 수정하지 않습니다. 최종 작업 결과에서는 확인한 검증과 미확인 항목을 사실대로 보고합니다.
