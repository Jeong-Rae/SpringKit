# Minimalism

## 목표와 판단 기준

미니멀리즘은 **현재 요구사항을 완전하게 충족하는 해법 중, 시스템에 새롭게 남는 불필요한 복잡성을 최소화하는 설계·구현 활동**입니다. 최소 변경은 코드 줄 수만으로 결정하지 않습니다. 새 개념과 책임, 상태와 분기, 의존성, 결합도, 사용자가 동작을 이해하고 수정하는 데 필요한 비용까지 함께 판단합니다.

**최소 완결 해법**은 요구된 기능과 수용 조건을 만족하고, 기존 계약·안전성·운영 제약을 보존하며, 그 안에서 추가적인 복잡성을 도입할 이유가 없는 해법입니다. 짧은 코드라도 오류 처리를 빠뜨리거나 책임을 흩어 놓았다면 탈락시킵니다. 반대로 코드가 더 길어도 책임과 검증이 명확하고 전체 유지 비용이 낮다면 선택할 수 있습니다.

최소화는 정해진 작업 범위에서 반복합니다. 요구를 충족한 뒤에는 불필요한 구성요소를 한 번 더 살피되, 추측한 미래 요구나 주변 코드의 무관한 정리를 위해 범위를 넓히지 않습니다.

## 판단 알고리즘

사용자가 이 스킬을 직접 호출한 작업에서 다음 순서로 행동합니다. 각 단계의 출력은 다음 판단의 입력으로 사용하고, 근거 없는 대안 탐색을 반복하지 않습니다.

1. **Understand: 요구와 실제 맥락을 파악합니다.** 사용자가 관찰할 결과, 수용 조건, 관련 코드와 호출자, 설정·테스트·배포 조건을 확인합니다. 무엇을 완성해야 하는지와 변경의 영향 범위를 구분합니다. (`NEC-01`, `COM-01`)
2. **Constrain: 줄일 수 없는 조건을 고정합니다.** 사용자 요구, 프로젝트의 기존 계약과 책임 경계, 입력 검증, 보안, 데이터 보존, 예상 운영 부하를 확인합니다. 이 조건을 만족하지 못하는 해법은 후보에서 제외합니다. (`COR-01`~`COR-03`)
3. **Simplify: 유효한 해법을 순서대로 찾습니다.** 이미 충족된 요구라면 변경이 필요한지 판단하고, 기존 도메인 행위·구성요소 → 표준 라이브러리·플랫폼 → 설치된 의존성 → 최소 신규 구현 순으로 검토합니다. 현재 요구를 완결하고 제약과 책임 경계를 지키는 첫 번째 해법을 기본으로 선택합니다. 다른 해법이 결합도·상태·유지 비용을 실질적으로 낮출 근거가 있을 때만 비교를 계속합니다. (`NEC-02`, `REU-01`~`REU-03`, `SIM-02`)
4. **Implement: 필요한 책임만 구현합니다.** 기존 구조와 도메인 행위를 존중하고, 코드와 상태를 적절한 책임에 모읍니다. 호출자, 테스트, 설정 등 기능 완결에 필요한 변경을 함께 수행합니다. 분기나 추상화는 실제 복잡성이 줄어들 때만 도입합니다. (`SIM-01`~`SIM-04`, `COM-01`, `COM-02`)
5. **Verify & Stop: 결과를 검증하고 종료합니다.** 수용 조건과 영향받는 호출 경로를 확인하고 위험에 비례하는 검증을 수행합니다. 실패하면 해당 판단으로 돌아가 수정합니다. 충족되었다면 추가 변경의 구체적인 이득이 없는 지점에서 종료하고, 확인한 결과와 남은 위험만 보고합니다. (`COR-04`, `COM-03`, `NEC-03`)

## 규칙 적용 계약

- 아래 인덱스의 **항상** 규칙은 매 작업에 적용합니다. **조건부** 규칙은 표의 적용 조건을 충족할 때 의무적으로 적용합니다. 다른 규칙을 적용하려고 조건을 인위적으로 만들지 않습니다.
- 인덱스를 통해 해당 작업의 규칙 코드를 식별합니다. 해당 범주의 구체적인 판단이나 실행이 필요한 경우 연결된 `references/` 문서의 동일 코드 지침을 읽습니다. 관련 없는 문서는 로드하지 않습니다.
- 규칙을 따른 결과는 코드, 설계 선택, 검증 또는 작업 중단으로 나타나야 합니다. 규칙 코드만 열거하거나 형식적인 점검표를 출력하는 것으로 대체하지 않습니다.
- 규칙이 충돌하면 요구사항과 프로젝트 지침을 존중하되, 안전성과 계약 및 완결성을 해치는 코드 축소는 선택하지 않습니다. 근거가 없으면 불필요한 일반화와 기능 확장도 선택하지 않습니다.

## 완료 조건

**완결 판정:** 요청된 모든 관찰 가능한 동작을 제공하고, 영향을 받는 호출 경로와 필수 제약을 보존하며, 적절한 검증 결과 또는 검증할 수 없었던 부분을 확인합니다.

**종료 판정:** 완결된 해법에 비해 추가 변경이 불필요한 개념·결합도·위험을 실질적으로 줄인다는 근거가 없다면 작업을 끝냅니다. 추가 리팩터링을 다음 작업의 요구로 만들어 내지 않습니다.

예를 들어, 줄 수를 줄이면서 신뢰 경계의 입력 검증을 삭제하는 변경은 탈락합니다. 기존 공개 행위 하나를 재사용해 같은 요구를 충족하고 호출자 계약을 유지하는 대안이 있다면, 새로운 추상화를 만드는 대신 이를 선택합니다.
