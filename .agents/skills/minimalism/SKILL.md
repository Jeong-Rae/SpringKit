# Minimalism

## 목표와 기준

미니멀리즘은 **현재 요구사항과 필수 계약을 완전하게 충족하는 해법 중, 시스템에 새롭게 남는 불필요한 복잡성을 최소화하는 설계·구현 활동**입니다. 코드 줄 수뿐 아니라 새로운 책임, 개념, 상태, 분기, 의존성, 결합도와 변경 비용을 고려합니다.

**최소 완결 해법**은 요구된 동작과 수용 조건을 만족하고, 기존의 책임 경계·호출자 계약·보안·데이터 보존·실제 운영 제약을 유지하며, 더 큰 구현 범위가 요구로 정당화되지 않는 해법입니다. 필요한 책임을 분명하게 표현하는 코드는 줄 수가 늘어나도 유지할 수 있습니다.

**작업 클로저(Closure)**는 하나의 수정 책임 경계를 정하고, 그 경계에서 필요한 호출자·테스트·설정까지 포함해 독립적으로 검증할 수 있는 작업 범위입니다. 이 용어는 언어의 함수 클로저와 구별합니다. Fixing에서는 원인이 관찰된 위치와 원인 책임 위치가 서로 다를 수 있으므로, 가능한 작업 클로저를 사용자에게 먼저 제안합니다.

## 작업 분기

사용자가 스킬을 호출하면 작업 의도를 구분하여 **하나의 주된 알고리즘**을 선택합니다.

| 작업 | 판단 기준 | 실행 |
| --- | --- | --- |
| **Editing** | 새 기능, 요구된 동작 변경, 코드 정리·리팩터링처럼 새로운 상태를 만드는 작업 | [Editing: A 점진적 확장 탐색](#editing-a-점진적-확장-탐색) |
| **Fixing** | 현재 동작이 기존 계약·기대 결과와 다르다는 문제를 조사하고 수정하는 작업 | [Fixing: C 책임·클로저 탐색](#fixing-c-책임클로저-탐색) |

동일한 요청에 두 종류의 작업이 있으면 작업 범위를 구분합니다. Editing 중 새로 작성한 코드의 검증이 실패하면 Editing 탐색으로 돌아갑니다. 기존 코드의 별도 결함을 발견했다면 이를 Fixing 작업으로 구분하여 클로저 제안 절차를 적용합니다. 분석·리뷰만 요청받았다면 코드를 변경하지 않고 관련 규칙으로 판단합니다.

## Editing: A 점진적 확장 탐색

**점진적 확장 탐색**은 가장 작은 구현 후보에서 시작하여, 충족하지 못한 실제 요구·계약이 확인될 때에만 변경 범위를 확장하는 방법입니다. 후보가 기능 규모에 따라 수학적으로 정렬된다는 뜻은 아닙니다. 어느 책임에서 구현해야 하는지와 무엇을 새로 도입해야 하는지를 함께 판단합니다.

1. **요구 확정:** 사용자가 관찰할 동작, 수용 조건, 관련 호출 경로와 보존할 계약을 확인합니다. (`NEC-01`, `COM-01`, `COR-01`~`COR-03`)
2. **최소 후보 탐색:** 요구가 기존 동작으로 이미 충족되는지 확인합니다. 필요한 변경이 있다면 **기존 코드 직접 사용 → 기존 책임의 행위 수정 또는 필요한 최소 Adapter·Decorator로 조합 → 표준·플랫폼 기능과 설치된 의존성 활용 → 새 라이브러리 검토 → 최소 신규 구현** 순으로 유효한 방법을 찾습니다. Adapter·Decorator는 실제 계약 차이나 부가 행동이 있을 때만 도입합니다. (`REU-01`~`REU-03`, `SIM-02`)
3. **필요한 만큼 확장:** 최소 후보가 수용 조건이나 계약을 충족하지 못한다면 **부족한 조건을 특정**하고 그 조건을 충족하는 책임·기능·구현 범위만 확장합니다. 더 깊은 수정이 정확한 책임에 해당한다면 수정 위치를 옮깁니다. 근거 없는 기능과 확장 지점을 추가하지 않습니다. (`NEC-02`, `SIM-01`~`SIM-03`)
4. **구현 및 완결:** 선택한 범위의 행위를 구현하고 변경된 호출자·테스트·설정·고정 데이터를 함께 반영합니다. (`SIM-01`~`SIM-04`, `COM-01`)
5. **검증과 종료:** 관련 테스트와 계약을 검증합니다. 실패 조건이 나타나면 그 조건에 필요한 범위로 돌아가 보완합니다. 충족되었다면 무관한 리팩터링 없이 작업을 종료하고 확인 결과를 보고합니다. (`COR-04`, `COM-03`, `NEC-03`)

예: 검색 조건 하나를 추가할 때 기존 검색 구성요소가 요구한 입력과 결과를 제공한다면 이를 사용합니다. 입력 계약에 차이가 확인되면 그 차이에 필요한 조합 또는 기존 행위의 수정만 검토합니다.

## Fixing: C 책임·클로저 탐색

**양방향 책임 탐색**은 오류가 드러난 실행 경로를 따라 원인 후보를 추적하는 동시에, 기존 계약과 불변식에서 출발해 원래 책임을 가진 객체·계층을 확인하는 방법입니다. 국소 수정부터 아키텍처 변경까지 모두 후보가 될 수 있지만, 실제 코드와 확인된 현상으로 뒷받침되는 범위만 제안합니다.

1. **현상 확인:** 기대 결과·실제 결과·재현 입력·실패 테스트·관련 로그를 조사합니다. 확인된 사실과 아직 확인하지 못한 원인 가설을 구분합니다. (`NEC-01`, `COR-01`, `COR-04`)
2. **원인과 책임 추적:** 증상이 나타난 코드에서 호출자·피호출자·데이터 이동을 따라 원인 후보를 추적합니다. 반대 방향에서는 계약·불변식으로부터 책임을 가진 객체와 경계를 찾아 두 경로를 대조합니다. (`SIM-01`, `COM-01`, `COM-02`)
3. **작업 클로저 도출:** 확인한 책임 위치별로 독립적으로 검증 가능한 수정 범위를 구성합니다. 호출부·기존 도메인 행위·공유 구성요소·아키텍처 경계는 **실제 근거가 있을 때만** 후보에 포함합니다. 각 범위에 필요한 호출자와 검증 대상을 식별합니다. (`COM-01`, `COM-02`)
4. **사용자에게 먼저 제안:** 코드 수정에 앞서 각 클로저를 **「제안」과 「제안의 근거」 두 항목만으로** 제시합니다. 제안에는 수정할 책임과 범위를, 근거에는 확인된 파일·호출 관계·재현 결과·테스트 등 사실을 작성합니다. 장단점, 트레이드오프, 후보 순위, 가치 판단, 예상되는 긍정적·부정적 결과를 덧붙이지 않습니다. 확인하지 못한 사항은 사실처럼 단정하지 않습니다. 사용자가 별도로 평가를 요청했을 때만 비교 평가를 수행합니다. ([완결성 지침](references/completeness.md))
5. **사용자의 범위 선택:** 사용자가 클로저를 선택할 때까지 Fixing 코드 수정을 보류합니다. 사용자가 이미 특정 작업 범위를 명시적으로 선택한 경우에는 같은 선택을 다시 요구하지 않습니다. 선택한 범위에서만 Editing의 A 탐색을 실행합니다.
6. **검증 및 경계 재확인:** 선택한 클로저와 연결된 계약·호출 경로를 검증합니다. 추가 책임 범위의 변경이 필요하다는 사실이 확인되면 기존 선택 경계를 넘어 수정하기 전에 새로운 클로저를 같은 형식으로 제안합니다. (`COR-04`, `COM-03`)

Fixing의 제안 형식은 다음과 같습니다. 제안별로 두 항목 외의 평가 문단을 만들지 않습니다.

> **클로저: API 응답 변환**
>
> **제안:** `OrderController`의 응답 금액 변환 행위를 수정합니다.
>
> **제안의 근거:** `OrderController`에서 `OrderPrice`의 계산값을 응답 값으로 변환하며 이 과정에 반올림 연산이 존재합니다.
>
> **클로저: 도메인 금액 계산**
>
> **제안:** `OrderPrice`의 금액 계산 행위와 관련 테스트를 수정합니다.
>
> **제안의 근거:** `OrderController`와 `SettlementService`가 `OrderPrice`의 계산 행위를 호출합니다.

위 예시는 가상의 코드 관계입니다. 실제 제안에서는 저장소에서 확인한 근거만 사용합니다.

## 규칙 적용 계약

- 아래 인덱스의 **항상** 규칙은 모든 작업에 적용합니다. 조건부 규칙은 적용 조건이 확인될 때 준수합니다.
- 인덱스에서 관련 코드와 참조 파일을 찾아 해당 판단에 필요한 지침만 읽습니다. **Fixing의 클로저 제안 시에는 [완결성](references/completeness.md)의 제안 계약을 반드시 확인합니다.** 관련 없는 참조는 읽지 않습니다.
- 규칙 적용 결과를 실제 설계 선택·구현·검증 또는 작업 중단에 반영합니다. 코드표의 반복이나 형식적인 체크리스트 출력을 수행 결과로 간주하지 않습니다.
- 안전성, 데이터 보존, 입력 검증, 호출자 계약, 프로젝트 지침과 사용자의 명시적 요구를 보존합니다. 다른 책임 범위의 작업을 추측하여 확장하지 않습니다.

## 완료 조건

**Editing:** 요청된 동작, 필수 제약과 영향받는 호출 경로가 검증되고, 실제 근거가 있는 추가 작업이 없으면 종료합니다.

**Fixing:** 클로저 제안과 사용자 선택을 완료한 뒤 선택된 범위에서 변경 및 검증을 수행합니다. 선택하지 않은 책임 범위로 수정하지 않습니다. 실행한 검증과 미확인 항목은 작업 결과에서 사실대로 보고합니다.
