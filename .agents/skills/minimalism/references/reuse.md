# 재사용 (REU)

Editing에서 새로운 구현 수단을 선택할 때 적용합니다. Fixing에서 사용자가 클로저를 선택한 뒤에도 같은 순서로 탐색합니다.

## 규칙 코드표

| 코드 | 점검 질문 | 지시 |
| --- | --- | --- |
| REU-01 | 저장소에 요구된 행동을 이미 제공하는 객체가 있는가? | 기존 객체의 공개 행위를 우선 직접 재사용합니다. |
| REU-02 | 기존 객체의 책임에서 필요한 차이를 수용할 수 있는가? | 기존 행위를 수정하거나 최소 변환·Adapter·Decorator로 조합합니다. |
| REU-03 | 프로젝트에서 사용할 수 있는 표준·플랫폼·설치된 기능이 있는가? | 이미 제공되는 기능과 프로젝트의 공개 계약을 활용합니다. |
| REU-04 | 신규 라이브러리가 필요한 기능을 제공하는가? | 도입과 직접 구현의 실제 유지·검증 비용을 확인합니다. |

## 실행 지침

- **REU-01:** 변경 경로와 관련 구현을 검색합니다. 기존 객체의 공개 행동을 사용하고 내부 데이터 구조를 호출자가 연쇄 탐색하게 만들지 않습니다. 동일한 역할의 서비스를 중복해서 작성하지 않습니다.
- **REU-02:** 필요한 동작이 기존 객체의 책임이면 그 객체의 행위를 수정하는 방법을 검토합니다. 기존 공개 계약과 새 호출 계약의 실제 차이가 있으면 최소 변환 함수를 사용합니다. 인터페이스 연결에는 Adapter를, 기존 계약을 유지한 부가 행동의 조합에는 Decorator를 검토합니다. 특별한 변환이나 부가 행동이 없다면 위임 전용 래퍼를 만들지 않습니다.
- **REU-03:** 표준 라이브러리·플랫폼 기능과 이미 설치된 의존성을 확인합니다. 프로젝트 내부에서 해당 기능을 감싼 공개 컴포넌트가 있다면 그 계약과 기존 관례를 확인합니다. 기존 구현을 복제하지 않습니다.
- **REU-04:** 새 라이브러리가 해결하는 실제 요구, 지원 환경, 보안 업데이트, 라이선스와 운영·검증 비용을 확인합니다. 필요 기능을 검증된 라이브러리로 해결하는 방법과 최소 신규 구현을 비교합니다. 암호화 등 전문적으로 검증된 구현을 임의로 재작성하지 않습니다.

## Editing의 후보 탐색

**후보를 찾는 순서:** 기존 코드 직접 사용 → 기존 책임 수정 또는 최소 적응 → 표준·플랫폼·설치된 기능 → 새 라이브러리 도입 검토 → 최소 신규 구현.

이 순서는 모든 후보를 구현하라는 의미가 아닙니다. 각 후보가 수용 조건과 계약을 충족하는지 확인한 뒤 필요한 경우에만 다음 후보를 살핍니다. 새 라이브러리 도입을 검토했더라도 최소 신규 구현으로 충족하는 상황에서는 도입과 유지 비용을 실제 근거로 판단합니다.

예: 기존 조회 행위는 날짜 문자열을 받지만 새 호출자는 날짜 객체를 사용한다면, 입력 형식의 차이를 연결하는 최소 변환 함수를 검토합니다. 기존 조회 로직을 별도로 복제하지 않습니다.
