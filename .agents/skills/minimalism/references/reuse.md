# 재사용 (REU)

새 코드를 만들거나 외부 도구를 선택하기 전에 적용합니다.

## 규칙 코드표

| 코드 | 점검 질문 | 지시 |
| --- | --- | --- |
| REU-01 | 저장소에 필요한 동작을 제공하는 객체나 컴포넌트가 있는가? | 기존 공개 행위와 조합을 우선 사용합니다. |
| REU-02 | 표준 라이브러리, 플랫폼, 설치된 패키지가 문제를 해결하는가? | 주변 코드의 관례를 지키며 이미 제공되는 기능을 활용합니다. |
| REU-03 | 새 의존성이 자체 구현보다 확실한 이득이 있는가? | 사용 사례와 유지보수 비용을 근거로 결정합니다. |

## 실행 지침

- **REU-01:** 변경 경로와 관련 구현을 검색합니다. 기존 객체가 제공하는 행위를 호출하고 내부 데이터 구조를 호출자가 탐색하도록 만들지 않습니다. 한 기능을 위한 중복 서비스·도우미를 추가하지 않습니다.
- **REU-02:** 프로젝트 내부 구현 → 표준 라이브러리·플랫폼 기능 → 설치된 의존성 순으로 검토합니다. 기존 컴포넌트가 표준 기능을 감싼 경우 프로젝트의 공개 계약과 관례를 우선합니다.
- **REU-03:** 새 의존성의 용량보다 필요한 기능, 보안 유지, 업데이트, 라이선스, 운용 비용을 판단합니다. 작은 기능을 위한 신규 패키지는 가능한 한 피하되, 암호화 같은 검증된 전문 구현을 임의로 대체하지 않습니다.

## Editing의 재사용 탐색 (REU-01~03)

| 후보 | 선택을 확인할 사실 |
| --- | --- |
| 기존 코드 직접 사용 | 요구된 행동과 이미 제공하는 공개 계약의 일치 |
| 기존 행위 수정 | 현재 객체가 해당 책임을 소유하며 변경되는 호출자 계약의 범위 |
| Adapter 또는 Decorator 조합 | 기존 인터페이스와 필요한 인터페이스의 차이 또는 추가해야 할 부가 행동 |
| 표준·플랫폼 기능 또는 설치된 의존성 | 현재 프로젝트에서 이용 가능한 기능과 기존 관례 |
| 새 라이브러리 도입 | 검증된 기능의 존재, 라이선스·업데이트·운영 제약 |
| 최소 신규 구현 | 앞선 후보로 충족하지 못한 실제 요구와 구현해야 할 책임 |

**Adapter**는 서로 다른 기존 인터페이스를 연결할 때, **Decorator**는 기존 공개 계약을 유지하며 부가 행동을 조합할 때 검토합니다. 실제 차이가 한 개의 함수로 표현된다면 그 함수만 추가합니다. 특별한 변환이나 부가 행동이 없다면 별도 래퍼를 만들지 않습니다.

예: 기존 날짜 조회 기능이 문자열 날짜를 받지만 새 호출자는 날짜 객체를 사용한다면, 기존 조회 행위를 호출하는 최소 변환 함수를 검토합니다. 기존 날짜 조회 행위를 복제하지 않습니다.
