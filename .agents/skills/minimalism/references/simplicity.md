# 단순성 (SIM)

책임과 코드를 쉽게 이해하고 수정할 수 있는 구조로 유지할 때 적용합니다.

## 규칙 코드표

| 코드 | 점검 질문 | 지시 |
| --- | --- | --- |
| SIM-01 | 변경된 책임이 적절한 객체와 위치에 모여 있는가? | 도메인 행위와 상태의 응집도를 유지합니다. |
| SIM-02 | 현재 요구로 정당화되지 않는 계층이나 우회 코드가 있는가? | 추측한 추상화·래퍼·옵션을 덜어냅니다. |
| SIM-03 | 조건 분기나 상태 전이가 실제로 반복·복잡한가? | 단순해지는 경우에만 데이터 테이블·상태 머신을 검토합니다. |
| SIM-04 | 코드를 처음 읽는 사람이 동작과 이유를 따라갈 수 있는가? | 이름·배치·주석을 이해 비용 기준으로 정리합니다. |

## 실행 지침

- **SIM-01:** 책임을 기준으로 객체와 메서드를 구성합니다. 함께 변경되는 상태와 행위를 한곳에 둡니다. 서로 다른 책임은 분리하되 줄 수를 줄이기 위한 분할은 하지 않습니다. 기존 계층의 역할과 협력 경계를 보존합니다.
- **SIM-02:** 현재 구현이 하나뿐이라는 이유만으로 인터페이스·팩토리·어댑터를 만들지 않습니다. 단, 이미 확립된 프로젝트 경계와 명시적인 확장 요구를 존중합니다. 불필요한 타입 변환과 전달 전용 래퍼를 제거합니다.
- **SIM-03:** 반복적인 조건부 매핑에는 테이블을, 다수의 상태와 전이에는 명시적 상태 모델을 비교합니다. 대안의 분기 수·규칙 중복·변경 비용이 실제로 줄어들 때만 채택합니다. 단순한 분기는 그대로 둡니다.
- **SIM-04:** 의미가 드러나는 이름과 관련된 코드의 근접 배치를 우선합니다. 알아보기 어려운 한 줄 표현을 피합니다. 주석에는 코드가 설명하지 못하는 이유와 제약만 기록하고 공백·정렬·쉼표는 프로젝트 포매터에 맡깁니다.

## 복잡성 비교 (SIM-01~04)

**비교 대상:** 현재 요구와 필수 제약을 모두 만족하는 해법만 비교합니다. 유효하지 않은 더 짧은 해법은 후보에서 제외합니다.

| 판단 요소 | 확인할 비용 |
| --- | --- |
| 개념과 책임 | 새로 이해해야 할 타입·역할·암묵적인 약속 |
| 상태와 분기 | 유지해야 하는 상태 수, 전이 규칙과 분기 중복 |
| 의존성과 결합 | 추가 라이브러리·설정·연쇄 변경의 범위 |
| 가독성과 검증 | 동작을 파악하고 오류를 재현·수정하는 부담 |

첫 번째 유효한 해법을 기본으로 채택합니다. 다른 후보가 위 비용을 실질적으로 줄이는 경우에만 더 비교합니다. 코드 줄 수와 파일 수는 같은 목적과 제약을 만족하는 후보 사이에서 참고 지표로 사용합니다.

예: 읽기 어려운 한 줄 조건식을 의미 있는 두 개의 함수로 표현해 책임과 실패 조건이 분명해진다면, 줄 수가 늘어나도 더 단순한 해법일 수 있습니다. 반면 현재 호출자가 하나라는 이유만으로 중간 인터페이스를 새로 만드는 것은 별도의 근거가 필요합니다.
