# 원인·클로저 (LOC)

Fixing에서 증상의 원인과 수정 책임을 조사하고 사용자에게 수정 범위를 제안할 때 적용합니다. Editing 중 발견한 기존 코드의 별도 결함에도 적용합니다.

## 규칙 코드표

| 코드 | 점검 질문 | 지시 |
| --- | --- | --- |
| LOC-01 | 증상이 나타난 위치와 계약을 책임지는 위치는 각각 어디인가? | 실행 경로와 계약·불변식을 양방향으로 추적하고 확인된 사실을 구분합니다. |
| LOC-02 | 어떤 책임 경계를 독립적으로 수정·검증할 수 있는가? | 근거가 있는 작업 클로저를 구성하고 제안·근거만 제시하여 사용자 선택을 받습니다. |

## 실행 지침

- **LOC-01:** 재현 입력·기대 결과·실제 결과를 확인합니다. 증상이 나타난 함수에서 호출자·피호출자·데이터 이동을 따라 조사하고, 계약과 불변식을 가진 객체에서 책임 위치를 역추적합니다. 실제 실행·테스트·로그·코드로 확인된 사실과 아직 검증하지 못한 가설을 구분합니다. 근본 원인이 확정되었다고 추측하지 않습니다.
- **LOC-02:** 확인된 책임 위치마다 해당 동작과 영향받는 호출자·테스트·설정까지 포함하는 **작업 클로저**를 정합니다. 각 클로저의 수정 대상과 확인한 근거를 적습니다. 국소 호출부, 기존 도메인 행위, 공유 컴포넌트, 아키텍처 경계는 실제 해당 책임의 근거가 있을 때만 후보로 구성합니다. 확인된 후보가 하나라면 하나만 제시합니다.

## 작업 클로저의 경계

작업 클로저는 수정할 책임과 그 수정의 완결성을 검증하는 데 필요한 범위입니다. **클로저는 수정 파일 하나와 동의어가 아닙니다.** 하나의 도메인 행위 변경에 여러 호출자의 계약 검증이 포함될 수 있습니다.

원인이 불명확하면 확인한 증거를 바탕으로 **조사 작업 클로저**를 제안할 수 있습니다. 코드 변경을 전제하는 클로저와 원인을 추가 조사하는 클로저를 구별합니다. 조사 결과가 확정되기 전에는 수정 효과를 단정하지 않습니다.

## 사용자 제안 계약 (LOC-02)

**Fixing의 코드 변경보다 클로저 제안이 먼저입니다.** 제안별로 다음 두 항목만 작성합니다.

- **제안:** 수정하거나 조사할 책임, 행위, 파일·계층과 필요한 검증 범위를 명시합니다.
- **제안의 근거:** 해당 후보를 도출한 파일 위치, 호출 관계, 관찰한 입출력, 로그 또는 테스트의 사실을 기술합니다. 미검증 원인 가설은 사실로 표현하지 않습니다.

제안 단계에서는 장단점, 트레이드오프, 후보 순위, 가치 판단, 미래 결과의 긍정·부정적 예측을 작성하지 않습니다. 사용자가 평가를 따로 요청한 경우에만 평가를 제공합니다. 확인한 사실의 범위를 넘어서는 암시적 판단을 덧붙이지 않습니다.

사용자가 범위를 선택할 때까지 Fixing 코드를 변경하지 않습니다. 사용자가 이미 특정 클로저를 명시적으로 선택했다면 동일한 선택을 반복해서 요청하지 않습니다. 선택한 범위에서 Editing 알고리즘을 실행하고, 다른 책임 범위의 변경이 필요해지면 새 클로저를 같은 형식으로 제안합니다.

## 제안 예시

다음은 가상의 호출 관계를 가정한 형식 예시입니다. 실제 작업에서는 저장소에서 확인한 이름과 근거를 사용합니다.

**클로저: API 응답 변환**

- **제안:** `OrderController`의 응답 금액 변환 행위와 해당 응답 테스트를 수정합니다.
- **제안의 근거:** `OrderController`는 `OrderPrice`에서 반환된 금액에 반올림을 적용하여 응답 값을 구성합니다.

**클로저: 도메인 금액 계산**

- **제안:** `OrderPrice`의 금액 계산 행위와 관련 호출 경로의 테스트를 수정합니다.
- **제안의 근거:** `OrderController`와 `SettlementService`가 `OrderPrice`의 계산 행위를 호출합니다.
