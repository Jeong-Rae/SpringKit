# 원인/클로저 (LOC)

Fixing에서 증상과 책임을 조사하고 사용자에게 변경할 작업 범위를 제안할 때 적용합니다. Editing 중 발견한 기존 코드의 별도 결함에도 적용합니다.

## 규칙 코드표

| 코드 | 점검 질문 | 지시 |
| --- | --- | --- |
| LOC-01 | 증상이 나타난 위치와 계약을 책임지는 위치는 각각 어디인가? | 실행 경로와 계약/불변식을 양방향으로 추적하고 확인된 사실을 구분합니다. |
| LOC-02 | 어떤 책임 경계를 독립적으로 수정/검증할 수 있는가? | 근거가 있는 작업 클로저를 구성하고 제안/근거만 제시하여 사용자 선택을 받습니다. |

## 규칙 실행 계약

### LOC-01 - 원인과 책임 위치 탐색

- **적용 조건:** Fixing에서 기존 동작과 기대 계약의 차이를 조사합니다.
- **수행 행동:** 증상 위치에서 호출자/피호출자/데이터 흐름을 추적하고, 요구 계약/불변식에서 해당 행위를 소유한 책임 객체를 역추적합니다. 확인한 사실과 미검증 원인 가설을 구분합니다.
- **판단 증거:** 재현 입력, 기대/실제 결과, 소스 코드 위치, 호출 관계, 실패 테스트 또는 실행 로그. 재현되지 않은 경우 그 상태도 기록합니다.
- **다음 전이:** 책임 경계 후보와 근거가 있으면 `LOC-02`로 이동합니다. 근거가 부족하면 조사할 경계를 `LOC-02`의 조사 클로저로 제안합니다.

### LOC-02 - 클로저 제안과 사용자 선택

- **적용 조건:** `LOC-01`에서 수정 또는 추가 조사할 책임 경계 후보와 확인된 근거를 확보했습니다.
- **수행 행동:** 실제 책임 위치별로 수정/조사 범위를 구성하고, **각 클로저마다 정확히 두 필드** `제안`과 `제안의 근거`를 작성합니다. 확인한 클로저가 하나면 하나만 제시합니다. 사용자가 선택할 때까지 Fixing 코드를 변경하지 않습니다.
- **판단 증거:** 근거가 되는 파일/메서드/호출 관계/관찰 결과와 각 범위에 포함되는 검증 대상. 근거의 사실 여부를 확인하고 가설을 확정 사실로 표현하지 않습니다.
- **다음 전이:** 사용자가 클로저를 선택하면 선택된 범위에서 Editing(A)으로 이동합니다. 이미 범위를 명시적으로 선택했다면 재선택을 요구하지 않습니다. 새로운 책임 변경이 필요한 경우 새 클로저를 제안하고 선택을 받습니다.

## 작업 클로저와 제안 형식

**작업 클로저**는 하나의 책임과 그 변경을 검증하는 데 필요한 호출자/테스트/설정의 범위입니다. 수정 파일 수와 관계없이 책임 경계를 기준으로 구성합니다. 원인이 확인되지 않은 경우에는 **조사 작업 클로저**를 구성할 수 있습니다.

사용자에게는 아래 **두 항목만** 제시합니다. 클로저 제목은 식별용으로 사용할 수 있습니다.

- **제안:** 변경/조사할 행위, 책임 객체 또는 계층과 해당 범위에서 확인할 검증 대상을 기술합니다.
- **제안의 근거:** 직접 확인한 코드 위치/호출 관계/재현 입력/로그/테스트 결과를 기술합니다.

제안 단계의 내용은 확인된 사실로 구성합니다. 장단점/트레이드오프/순위/가치 판단/예상 미래 결과의 평가는 사용자가 별도로 요청할 때 수행합니다. 코드 위치가 확인되지 않았다면 확인되지 않았다는 사실과 조사 가능한 경계만 기술합니다.

## 제안 예시

다음 예시는 가상의 저장소와 호출 관계를 사용합니다.

**클로저: API 응답 변환**

- **제안:** `OrderController`의 응답 금액 변환 행위와 해당 응답 테스트를 수정합니다.
- **제안의 근거:** `OrderController`에서 `OrderPrice`의 반환 금액에 반올림을 적용하여 응답 값을 구성합니다.

**클로저: 도메인 금액 계산**

- **제안:** `OrderPrice`의 금액 계산 행위와 관련 호출 경로의 테스트를 수정합니다.
- **제안의 근거:** `OrderController`와 `SettlementService`에서 `OrderPrice`의 계산 행위를 호출합니다.

**클로저: 원인 추가 조사**

- **제안:** `OrderController`에서 `OrderPrice`로 이어지는 금액 전달 경로의 입력과 출력, 관련 테스트를 조사합니다.
- **제안의 근거:** `OrderController`에서 응답 금액이 달라지는 현상이 보고되었고, 확인된 코드에서 `OrderPrice`를 호출합니다. 원인 위치는 아직 확인되지 않았습니다.
